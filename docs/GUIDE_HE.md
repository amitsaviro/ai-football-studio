# מדריך לפרויקט: AI Football Studio

המדריך מסביר מה בנינו, איך החלקים מתחברים, ובאילו טכנולוגיות השתמשנו ולמה.
מומלץ לקרוא לפי הסדר, ולפתוח כל קובץ שמוזכר תוך כדי קריאה.

---

## 1. הרעיון בשורה אחת
פאנל של פרשני AI שמתווכחים על ליגת העל, כשכל מספר שהם אומרים מגיע מבסיס נתונים אמיתי ולא מהזיכרון של המודל.

## 2. התמונה הגדולה: איך מידע זורם במערכת

```
 Goal API (אינטרנט)
      │  ① ingest.py מושך נתונים פעם ביום
      ▼
 ┌─────────────── Postgres ───────────────┐
 │  raw.api_responses   ← התשובות הגולמיות │
 │        │ ② נרמול + איחוד שחקנים          │
 │        ▼                                │
 │  teams / players / fixtures /           │
 │  lineups / goals / match_stats          │
 └────────────────────────────────────────┘
      ▲  ③ הכלים (tools) שולפים נתונים
      │
 app/tools/  ← league_table, top_scorers, run_sql ...
      ▲  ④ Claude מבקש להפעיל כלי
      │
 app/agents/pundit.py  ← לולאת הסוכן
      ▲  ⑤ שאלה מהמשתמש
      │
 scripts/ask.py (טרמינל) → בעתיד: שרת + ממשק React
```

שתי השכבות מופרדות בכוונה:
- **שכבת הדאטה** (שלבים ①–②) לא יודעת בכלל שיש AI.
- **שכבת ה-AI** (שלבים ③–⑤) לא יודעת מאיפה הדאטה הגיע.

כך אפשר להחליף ספק נתונים בלי לגעת בסוכנים, ולהחליף מודל בלי לגעת בדאטה.

## 4. עוברים על הקבצים, לפי סדר הקריאה המומלץ

### שלב א': הגדרות וחיבור
**`app/config.py`**
קורא את קובץ `.env` ומרכז את כל ההגדרות במקום אחד: כתובות DB, מפתחות API, איזה מודל של Claude להפעיל ו"כמה להתאמץ".
- **למה כך?** שאר הקוד לא קורא משתני סביבה ישירות. אם רוצים לשנות משהו, יש מקום אחד לחפש בו.
- **`@dataclass(frozen=True)`**: מחלקה שה-Python כותב לה את הקוד המשעמם לבד. `frozen` אומר שאי אפשר לשנות אותה בזמן ריצה.

**`app/db.py`**
שתי פונקציות: `connect()` פותחת חיבור ל-Postgres, ו-`init_schema()` מריצה את `schema.sql`.
- **`dict_row`** גורם לכל שורה לחזור כמילון (`{"name": "Dor Peretz", ...}`) ולא כ-tuple, וכך קל להפוך אותה ל-JSON.

### שלב ב': בסיס הנתונים
**`db/schema.sql`**: הקובץ הכי חשוב להבנת הפרויקט. שתי שכבות:
1. **`raw.api_responses`**: כל תשובה מה-API נשמרת כמו שהיא, בעמודת `jsonb` (JSON בתוך Postgres).
   - חוסך מכסה: אם כבר הורדנו משהו, לא מבקשים אותו שוב.
   - מאפשר לבנות את הטבלאות מחדש בלי אינטרנט (`--rebuild`).
   - משמש תיעוד: אפשר תמיד לבדוק מה בדיוק ה-API החזיר.
2. **הטבלאות המנורמלות**, שמהן הכלים שולפים:

| טבלה | מה יש בה | מפתח |
|---|---|---|
| `teams` | קבוצות | `id` |
| `players` | שחקנים ומאמנים. `display_name` מחושב אוטומטית ("E. Sokler" → "Sokler") | `key` |
| `player_aliases` | מפתחות כפולים שאוחדו, ולמי | `alias_key` |
| `fixtures` | משחקים: עונה, מחזור, תוצאה, מערכים | `id` |
| `lineups` | מי שיחק בכל משחק: פותח / ספסל / מאמן | `(fixture_id, player_key)` |
| `goals` | שערים: דקה, כובש, מבשל, פנדל | `id` |
| `match_stats` | סטטיסטיקות קבוצתיות למשחק, שורה לכל נתון | `(fixture_id, team_id, stat)` |

מושגים שכדאי להכיר:
- **Primary Key**: מזהה ייחודי לשורה.
- **Foreign Key (`REFERENCES`)**: קישור בין טבלאות. למשל `goals.fixture_id` חייב להיות משחק שקיים.
- **Index**: "תוכן עניינים" שמאיץ חיפוש לפי עמודה.
- **`ON DELETE CASCADE`**: אם משחק נמחק, גם השערים שלו נמחקים.
- **פורמט "ארוך" ב-`match_stats`**: שורה לכל נתון, במקום עמודה לכל נתון. אם ה-API יוסיף סוג סטטיסטיקה חדש, לא צריך לשנות את הטבלה.
- **Idempotent**: `CREATE TABLE IF NOT EXISTS` מאפשר להריץ את הקובץ שוב ושוב בלי שגיאות.
- **Extensions**: ‏`unaccent` מסיר סימנים מאותיות (Davó → Davo), ו-`pg_trgm` מודד דמיון בין מחרוזות, מה שמאפשר לסבול שגיאות כתיב.

**`db/readonly_role.sql`**: יוצר משתמש בשם `pundit_ro` שיכול **רק לקרוא** את הטבלאות, אין לו גישה ל-`raw`, ושאילתה שלו נעצרת אחרי 3 שניות. זה המשתמש ש-Claude מריץ איתו SQL.

### שלב ג': משיכת נתונים (Ingestion)
**`app/sources/goal_api.py`**: הלקוח של Goal API.
- `get()` בודקת קודם במטמון (`raw.api_responses`), ורק אם אין שם כלום שולחת בקשה ל-API ושומרת את התשובה.
- **מעקב מכסה:** ה-API מחזיר בכל תשובה כותרת (header) `x-ratelimit-remaining`, כמה בקשות נשארו היום. כשנשארות 20, הלקוח זורק `QuotaExhausted` והריצה נעצרת בצורה מסודרת.
- **מצב offline:** בזמן `--rebuild` מותר לקרוא רק מהמטמון.
- `get_all_pages()` מטפלת ב-**pagination**: ה-API מחזיר 100 פריטים בכל פעם, והפונקציה ממשיכה לבקש עם `offset` עד שמקבלת `hasMore=false`.

**`app/ingest/goal_api.py`**: הופך JSON גולמי לשורות בטבלאות.
- `sync_fixtures()`: כל המשחקים והקבוצות. תמיד מושך מחדש, כי תוצאות משתנות.
- `load_fixture_details()`: למשחק אחד, מושך הרכבים, שערים וסטטיסטיקות (3 בקשות).
- `sync_details()`: עובר על משחקים שחסרים להם פרטים, מהחדש לישן, עד שהמכסה נגמרת. ככה, כשמריצים פעם ביום, בסוף הכול מתמלא.
- **Upsert** (`INSERT ... ON CONFLICT DO UPDATE`): מכניס שורה, ואם היא כבר קיימת מעדכן אותה.
- **טיפול בדאטה "מלוכלך":** מפתח `0` = שחקן לא מזוהה ולכן מדלגים עליו; אסור להחליף שם מלא בשם מקוצר.

**`app/ingest/players.py`**: **זיהוי ישויות (Entity Resolution)**, החלק הכי "אלגוריתמי" עד עכשיו.
- **הבעיה:** ה-API נותן לפעמים לאותו שחקן כמה מזהים.
- **הכלל, שהגענו אליו יחד:** שני מפתחות הם אותו שחקן אם יש להם שם תואם ("D. Peretz" ≈ "Dor Peretz"), הם באותה קבוצה, והם **אף פעם לא הופיעו באותו הרכב באותו משחק**. אם הופיעו יחד, מדובר בשני אנשים שונים.
- **Union-Find:** מבנה נתונים קלאסי לאיחוד קבוצות. כל מפתח מתחיל כקבוצה משלו, וכל התאמה מאחדת שתי קבוצות. זו שאלה שחוזרת בראיונות טכניים.
- בסוף, לכל קבוצה נבחר מפתח "קנוני" (זה עם הכי הרבה הופעות), וכל ההפניות מתעדכנות אליו.

**`scripts/ingest.py`**: הפקודה שמריצים:
```bash
python scripts/ingest.py              # משיכה יומית
python scripts/ingest.py --rebuild    # בנייה מחדש מהמטמון, בלי אינטרנט
```

### שלב ד': הכלים של הפרשנים
**`app/tools/lookup.py`**: מתרגם שם חופשי למזהה ב-DB.
- `TEAM_ALIASES`: מילון שמות בעברית ("ביתר" → "Beitar Jerusalem").
- `find_player()` מדרג התאמות: שם מדויק = 1.0, שם משפחה בלבד = 0.9, דמיון (trigram) = בין 0 ל-1.
- **כשאין התאמה ברורה, לא מנחשים.** מחזירים רשימת מועמדים, והפרשן שואל למי הכוונה.

**`app/tools/stats.py`**: הכלים עצמם. כל פונקציה מחזירה `dict` שהופך ל-JSON.
- `league_table`, `top_scorers`, `player_stats`, `team_form`, `head_to_head`, `team_match_stats`, `match_report`, `data_coverage`.
- **הכול מחושב מהנתונים הגולמיים** (תוצאות ואירועי שערים), ולא מהסיכומים של ה-API שגילינו שהם שגויים.
- `_with_coverage_warning()`: אם עונה לא טעונה במלואה, מוסיפה לתוצאה אזהרה כדי שהפרשן לא יסיק מסקנות שגויות.
- **שגיאות הן מידע:** במקום לקרוס, כלי מחזיר `{"error": ...}`, ו-Claude קורא את השגיאה ומתקן את עצמו.

**`app/tools/sql.py`**: הכלי `run_sql`, שבו Claude כותב SQL בעצמו. **ארבע שכבות הגנה (Defense in Depth):**
1. משתמש DB לקריאה בלבד: גם אם כל השאר ייכשל, בסיס הנתונים עצמו יחסום.
2. טרנזקציה במצב read-only והגבלת זמן של 3 שניות.
3. מתקבלת רק שאילתת `SELECT` אחת, בלי `;`.
4. הגבלה ל-100 שורות ו-20,000 תווים, כדי שתשובה ענקית לא "תציף" את ההקשר של המודל.

**`app/tools/registry.py`**: "תפריט" הכלים ש-Claude מקבל.
- `TOOLS`: לכל כלי יש `name`, `description` (שמסביר ל-Claude **מתי** להשתמש בו) ו-`input_schema` (אילו פרמטרים הכלי מקבל, בפורמט JSON Schema).
- `call_tool()`: מקבל שם כלי ופרמטרים ומריץ את הפונקציה המתאימה.

### שלב ה': הפרשן (AI)
**`app/agents/personas.py`**: ה-**System Prompt**, ההוראות שמגדירות ל-Claude מי הוא.
- `GROUNDING_RULES`: כללים משותפים לכל הפרשנים. כל מספר מכלי, "אין לי נתונים" עדיף על ניחוש, לשאול כשיש עמימות.
- `STATISTICIAN`: האופי ("יבש, מדויק, פדנט") + הכללים.

**`app/agents/pundit.py`**: **לולאת הסוכן (Agent Loop)**, הלב של החלק ה"חכם":
```
1. שולחים ל-Claude: הפרסונה + הכלים + השאלה
2. Claude עונה באחת משתי דרכים:
   א. stop_reason = "tool_use" → "תפעיל לי את top_scorers"
      → מריצים את הכלי, שולחים את התוצאה, וחוזרים לשלב 1
   ב. stop_reason = "end_turn" → תשובה סופית → סיום
```
- **`yield` / Generator:** הפונקציה "פולטת" אירוע בכל צעד (`tool_call`, `tool_result`, `answer`) במקום להחזיר רק תשובה בסוף. בממשק זה יאפשר להציג בזמן אמת מה הפרשן עושה.
- **Prompt Caching** (`cache_control`): הפרסונה והכלים זהים בכל קריאה, ולכן Anthropic שומרת אותם במטמון. קריאה מהמטמון עולה 10% מהמחיר.
- **Adaptive Thinking + Effort:** Claude "חושב" לפני שהוא עונה, ו-`effort` קובע כמה. זה הכלי העיקרי לשליטה בעלות.
- **Fallbacks:** אם מנגנון בטיחות מסרב בטעות, הבקשה עוברת אוטומטית למודל חלופי.
- **`MAX_TOOL_ROUNDS = 8`:** מגבלה שמונעת מלולאה תקועה לבזבז כסף.
- **`Usage`:** סופר טוקנים ומחשב עלות, כדי שתמיד נדע כמה כל תשובה עלתה.

**`scripts/ask.py`**: ממשק טרמינל לפרשן. מציג כל כלי שהופעל ובסוף את העלות.

### שלב ו': בדיקות
**`tests/test_tools.py`**: בדיקות אוטומטיות עם `pytest`.
- **בדיקות אינווריאנטים:** בודקים דברים שחייבים להיות נכונים תמיד, לא משנה מה הדאטה. למשל "סך השערים שנכבשו בטבלה = סך השערים שספגו", או "נקודות = 3×ניצחונות + תיקו". כך הבדיקות לא נשברות כשמחזור חדש נטען.
- **בדיקות אבטחה:** 7 ניסיונות תקיפה על `run_sql`, ולכל אחד בדיקה שווידאה שנחסם ושהנתונים לא השתנו.
- הבדיקות כבר מצאו באג אמיתי (טבלת משחקי החוץ).

## 7. מילון מונחים

| מונח | הסבר |
|---|---|
| **API** | ממשק שבו תוכנה אחת מבקשת מידע מתוכנה אחרת (אצלנו: Goal API, Claude API) |
| **API Key** | "סיסמה" לשימוש ב-API. לא נכנס לקוד ולא ל-Git |
| **Rate limit / Quota** | כמה בקשות מותר לשלוח (אצלנו 1,000 ביום) |
| **Pagination** | חלוקת תוצאות לעמודים |
| **Ingestion / ETL** | משיכת נתונים, המרה לפורמט שלנו וטעינה ל-DB |
| **Normalization** | פירוק הנתונים לטבלאות מסודרות בלי כפילויות |
| **Entity Resolution** | זיהוי שכמה רשומות מתארות את אותה ישות (אותו שחקן) |
| **LLM** | מודל שפה גדול (Claude) |
| **System Prompt** | הוראות קבועות שמגדירות את התפקיד וההתנהגות של המודל |
| **Tool Use / Function Calling** | היכולת של המודל לבקש להריץ פונקציה בקוד שלנו |
| **Agent** | מודל שפועל בלולאה: חושב, מפעיל כלים, רואה תוצאות וממשיך |
| **Grounding** | עיגון התשובות בנתונים אמיתיים ולא בזיכרון של המודל |
| **Hallucination** | כשמודל ממציא מידע שנשמע אמין |
| **Token** | יחידת טקסט שהמודל עובד איתה (בערך חלק ממילה). לפיה משלמים |
| **Prompt Caching** | שמירת חלק קבוע של הבקשה במטמון כדי לחסוך בעלות |
| **Defense in Depth** | כמה שכבות הגנה, כך שכשל של אחת לא מספיק לפריצה |
| **Idempotent** | פעולה שאפשר להריץ שוב ושוב והתוצאה זהה |
| **Invariant** | תנאי שחייב להתקיים תמיד (בסיס לבדיקות שלנו) |

## 8. שאלות שסביר שתישאל בראיון, ואיפה התשובה

1. **"איך מנעת מה-AI להמציא נתונים?"** → Grounding: כל מספר מכלי, `data_coverage`, אזהרות על נתונים חלקיים (פרקים 4ד–4ה).
2. **"איך הגנת על ה-DB מ-SQL שהמודל כתב?"** → ארבע שכבות הגנה ב-`sql.py` + הבדיקות.
3. **"מה עשית כשהדאטה היה מלוכלך?"** → זיהוי ישויות ב-`players.py`, התעלמות מסיכומים שגויים של ה-API, מפתח `0`.
4. **"איך עבדת עם מגבלת בקשות?"** → מטמון `raw`, טעינה הדרגתית שממשיכה מאיפה שעצרה, מעקב מכסה.
5. **"כמה זה עולה ואיך שלטת בעלות?"** → Prompt caching, effort, מגבלת סבבים, מדידה ב-`Usage`.
6. **"איך בדקת שזה עובד?"** → בדיקות אינווריאנטים ובדיקות אבטחה ב-pytest.
7. **"למה כתבת לולאת סוכן בעצמך?"** → כדי להזרים כל צעד לממשק בזמן אמת.
